# محرك الهوية في Marketer AI — مواصفة مبنية على تفكيك سَهَل Ai

> **كيف تستخدم هذا الملف:** ضعه في مستودع Marketer AI تحت `docs/identity-engine-spec.md`، وأضف سطراً في `CLAUDE.md` يشير إليه. هذا الملف هو ذاكرة المشروع الخارجية — كل جلسة كلود تقرأه قبل أن تلمس محرك الهوية.
>
> كل ما تحته **[مقيس]** رُصد فعلياً في 46 تشغيلة على منصة سَهَل Ai (40 في مسار السلع + 6 في مسار الخدمات) مع اعتراض كامل لطلبات الشبكة. وكل ما تحته **[قرار]** هو ما يجب أن يفعله Marketer AI مختلفاً، ولماذا.

## 1. معمارية سَهَل Ai كما هي فعلياً

### 1.1 نقاط النهاية [مقيس]

```
GET  /subscriber/identity-setup/questions?type=products|services
     → تعريف الأسئلة (id, questionText, questionType, isRequired, options, questionOrder)

POST /subscriber/identity-setup/generate-ai          12–21 ثانية
     req: { businessType, answers:{ "<qid>": "<value>" }, questions:[ تعريف الأسئلة كاملاً ] }
     res: { success, shortDescription, detailedDescription, technicalDescription }

POST /subscriber/identity-setup/save                 ~0.8 ثانية، بلا ذكاء اصطناعي
     req: { businessType, answers, shortDescription, detailedDescription, technicalDescription }
```

**[مقيس]** التوليد **استدعاء واحد** يُرجع الطبقات الثلاث معاً. ليست أربعة استدعاءات ولا حرارات منفصلة.

**[مقيس]** `businessType` ومصفوفة `questions` **تُرسل من المتصفح**. الخادم يبني البرومبت من بيانات قادمة من العميل.

### 1.2 الطبقات [مقيس]

| الطبقة | المخرج | الطول المرصود |
|--------|--------|----------------|
| L0 | إجابات المستخدم الخام (5 أسئلة) | — |
| L1 | `technicalDescription` — سلسلة JSON بـ8 مفاتيح | 700–1100 حرف |
| L2 | `shortDescription` | جملتان بالضبط، 118–220 حرفاً، **40/40** |
| L3 | `detailedDescription` | 3 جمل (30/40)، 4 جمل (9/40)، 396–677 حرفاً |

### 1.3 مفاتيح L1 [مقيس]

```json
{
  "project_type": "...", "project_name": "...", "activity_type": "...",
  "selling_summary": "...", "competitive_advantages_instruction": "...",
  "ملاحظات_إضافية_مهمة": "...",      ← مفتاح عربي وسط مفاتيح إنجليزية
  "context_summary": "...",            ← لا تعرضه الواجهة إطلاقاً
  "store_url": "..."                   ← يُحذف المفتاح كلياً إذا كان الرابط فارغاً
}
```

**[مقيس]** الواجهة تعرض 7 حقول والخادم يُرجع 8. `context_summary` يُولَّد ويُحفظ ولا يراه صاحب المشروع أبداً.

### 1.4 القوالب الثابتة [مقيس]

- `competitive_advantages_instruction` يبدأ بـ«خذ بعين الاعتبار:» في **40/40** ويحتوي «كنقاط قوة إبداعية» في 39/40 → نص مثبّت في البرومبت، النموذج يملأ الفراغ فقط.
- 30/40 من الأوصاف التفصيلية تبدأ بأحد ثلاثة أفعال: ينطلق (12)، يأتي (10)، يقدّم (8).
- `ملاحظات_إضافية_مهمة` ليس وصفاً — إنه **بلوك تعليمات**: 28/40 قائمة مرقّمة، 18/40 فيها منع صريح («لا تضف منتجات غير مذكورة»).

### 1.5 الاستقرار والحساسية [مقيس]

عند إعادة إدخال **إجابات متطابقة حرفياً** (أرضية العشوائية):

| الطبقة | التطابق عند مدخلات متطابقة | عند إعادة صياغة بنفس المعنى | الفارق |
|--------|---------------------------|---------------------------|--------|
| `activity_type` | 89.4٪ | 64.3٪ | **‑25.1** |
| `selling_summary` | 88.9٪ | 71.1٪ | ‑17.8 |
| `competitive_advantages_instruction` | 68.4٪ | 57.3٪ | ‑11.1 |
| الوصف المبسط | 68.6٪ | 53.0٪ | ‑15.6 |
| **الوصف التفصيلي** | **13.0٪** | 15.3٪ | ≈0 |

قراءتان مهمتان:

1. **الوصف التفصيلي غير قابل للاستنساخ.** نفس المدخلات حرفياً تعطي نصاً مختلفاً كلياً. لا يمكن لعميل استعادة وصفه إن ندم على «إعادة التوليد».
2. **`activity_type` ينسخ ألفاظ المستخدم تقريباً كما هي.** مُدخل عامي «كفرات وقطع مكاين» خرج حرفياً «الفلاتر، البطاريات، الكفرات، وقطع المكاين». لا تطبيع للمصطلحات إطلاقاً.

### 1.6 أثر كل حقل [مقيس — تجربة المتغير الواحد]

| المتغيّر | `activity_type` | `selling_summary` | المزايا | القراءة |
|----------|-----------------|-------------------|---------|---------|
| المزايا فقط | 92.1٪ | 81.5٪ | **17.2٪** | تعيين 1:1 نظيف |
| «ماذا تبيع» فقط | **53.5٪** | **38.7٪** | 80.9٪ | المحرّك الرئيسي للتصنيف |
| الملاحظات فقط | 97.3٪ | 68.2٪ | 82.8٪ | لا يغيّر التصنيف لكنه **يعيد توجيه كل المحتوى** |
| **الرابط فقط** | **100٪** | **100٪** | 91.5٪ | **الرابط لا يُقرأ إطلاقاً** |
| الاسم فقط (عربي↔إنجليزي) | 100٪ | 91.3٪ | 26.6٪ | الاسم لا يؤثر على التصنيف |

### 1.7 سلوك الحالات الحدية [مقيس]

| الحالة | ما حدث |
|--------|--------|
| حقل إلزامي فارغ | الخادم **قبِله**. L1 كتب «لم تُذكر مزايا تنافسية محددة في المدخلات»، لكن **L2/L3 أنتجتا نصاً تسويقياً كامل الثقة** لا يستند لشيء |
| الاسم فقط | `activity_type` = «غير مذكور في المدخلات»، ومع ذلك وُلِّدت فقرة تبني شخصية من دلالة الاسم |
| مدخلات متناقضة | **رُصد التناقض** — لكن فقط داخل `context_summary` المخفي. المخرج الظاهر قدّم استوديو تصميم مصنّفاً كمكتب محاماة بلا تنبيه |
| مدخل إنجليزي | المخرج عربي دائماً، لغة المخرج مثبّتة في البرومبت |
| كلمة واحدة | وُلِّدت هوية كاملة من كلمة «سريع»، وطُبِّعت إلى «السرعة» |
| **حقن تعليمات** | **فشل الحقن.** النموذج حوّله إلى تعليمة مضادة داخل الحقل نفسه |

### 1.8 قيود المنتج [مقيس]

- نوع المشروع (سلع/خدمات) **غير قابل للتعديل** بعد الإعداد إلا بحذف نهائي للهوية.
- مسار الخدمات يستخدم **قائمة مغلقة من 13 تصنيفاً** بدل النص الحر → عيادة أسنان وعيادة أسرة كلتاهما «خدمات صحية وطبية» ولا شيء غير ذلك يصل للسياق.
- معرّفات الأسئلة غير متسلسلة (14، 28، 18، 25، 29 للسلع) → بنك أسئلة أكبر مُفلتر بـ`businessType`.
- الحقول `isRequired: true` تمرّ فارغة بلا أي تحقق.
- كل براند إضافي: 19$ شهرياً / 180$ سنوياً، بحد أقصى 20.

## 2. القرارات المعمارية لـ Marketer AI

### ق1 — توليد على مرحلتين فعليتين، لا استدعاء واحد

**المشكلة:** في سَهَل، القيود المكتوبة في L1 لا تقيّد L2/L3 لأنهما يُولَّدان في نفس الاستدعاء من نفس المدخل الخام.

**القرار:**

```
المرحلة 1 — الاستخلاص (extraction)
  مدخل: إجابات المستخدم + حقائق مستخرجة من الرابط
  مخرج: JSON مُتحقَّق منه بـ schema صارم
  حرارة: 0.1–0.2
  قاعدة: كل حقل غير مذكور يُكتب صراحة null + سبب، لا نص إنشائي

المرحلة 2 — الكتابة (writing)
  مدخل: مخرج المرحلة 1 فقط — لا يرى إجابات المستخدم الخام إطلاقاً
  قاعدة صلبة: أي حقل قيمته null ممنوع الكتابة عنه. إن كانت الحقول الأساسية null
             يُرجع المحرك "insufficient_input" ويُسأل العميل بدل توليد نص فارغ
```

**معيار قبول:** مدخل ناقص ⇒ لا نص تسويقي عنه. قابل للاختبار آلياً.

### ق2 — البرومبت والمخطط ملك الخادم

**المشكلة [مقيس]:** سَهَل يستقبل `businessType` و`questions` من المتصفح.

**القرار:** العميل يرسل `{brand_id, answers:{question_id: value}}` فقط. تعريف الأسئلة والبرومبت وقائمة التصنيفات كلها على الخادم. أي حقل زائد في الطلب يُرفض لا يُتجاهل.

### ق3 — مخطط JSON مُتحقَّق منه ومُصدَّر

**المشكلة [مقيس]:** مفتاح عربي وسط مفاتيح إنجليزية، ومفتاح `store_url` يختفي كلياً عند الفراغ.

**القرار:** كل المفاتيح `snake_case` إنجليزية. الحقل الفارغ `null` لا محذوف. تحقق بـ JSON Schema بعد كل توليد، وأعد المحاولة مرة واحدة عند الفشل ثم أرجع خطأ صريحاً. أضف `schema_version` لكل هوية.

### ق4 — اقرأ الرابط فعلاً

**المشكلة [مقيس]:** تغيير الرابط من موقع إلى إنستقرام لم يغيّر `activity_type` ولا `selling_summary` بنسبة 100٪ — سَهَل ينسخ الرابط كنص ولا يزوره.

**القرار:** عند وجود رابط، اسحب الصفحة واستخرج: الفئات، أسماء المنتجات، نطاق الأسعار، نبرة النصوص، لغة الموقع. مرّرها للمرحلة 1 كـ`source: website` مع تمييزها عن `source: user`. اعرض للعميل ما استُخرج ليؤكده.

**هذا أرخص وأوضح تمايز متاح.** العميل سيرى الفرق في أول دقيقة.

### ق5 — طبقة تطبيع المصطلحات

**المشكلة [مقيس]:** «كفرات» تبقى «كفرات»، و«قطع مكاين» تبقى كما هي، فيرث المحتوى التالي كل ركاكة صياغة العميل.

**القرار:** قاموس تطبيع عربي/خليجي → مصطلح معياري، يحفظ الاثنين: `user_term` و`canonical_term`. المحتوى التسويقي يستخدم المعياري، والسيو يستخدم الاثنين.

### ق6 — إصدارات الهوية

**المشكلة [مقيس]:** الوصف التفصيلي يتغيّر كلياً عند إعادة التوليد (13٪ تطابق)، ولا يوجد تراجع. إعادة التوليد تدمّر النسخة السابقة نهائياً.

**القرار:** جدول `identity_versions` لكل إصدار: المدخلات، المخرجات، نموذج الذكاء، البرومبت المستخدم، الطابع الزمني. واجهة: مقارنة + استعادة. ولا يُستبدل الإصدار النشط إلا بتأكيد صريح.

### ق7 — الهوية بنية تحتية لا إبداع

**القرار:** حرارة منخفضة لمرحلة الاستخلاص، وتخزين النتيجة بدل إعادة توليدها. أعِد التوليد فقط عند تغيّر المدخلات أو بطلب صريح. أما النصوص التسويقية فيُسمح فيها بالتنوع — لأنها مخرج نهائي لا سياق يُبنى عليه.

### ق8 — قواعد المحتوى حقول مهيكلة لا ملاحظة حرة

**المشكلة [مقيس]:** أقوى حقل في سَهَل هو «الملاحظات الإضافية» — وهو اختياري، آخر الأسئلة، ونص حر. تغييره وحده أعاد توجيه الهوية كلها.

**القرار:** فكّكه إلى حقول صريحة:

```
tone              : (رسمي | ودّي | عملي | فاخر)
hero_product      : نص
target_audience   : نص
must_mention[]    : قائمة
must_not_mention[]: قائمة   ← مثل: الأسعار، المنافسين، ادعاءات طبية
reading_level     : (بسيط | متوسط | متخصص)
```

ثم تُجمَّع هذه الحقول في البرومبت **برمجياً بقالب ثابت**، لا بتمرير نص المستخدم كتعليمات.

### ق9 — اعرض التناقض للعميل

**المشكلة [مقيس]:** سَهَل رصد التناقض بين التصنيف والمزايا وكتبه في حقل مخفي.

**القرار:** المرحلة 1 تُرجع `conflicts[]`. أي تعارض يظهر للعميل كتنبيه قبل الحفظ: «صنّفت نشاطك خدمات قانونية لكن مزاياك تصف تصميماً — أيهما الصحيح؟»

### ق10 — تحقق فعلي من الحقول الإلزامية

**المشكلة [مقيس]:** `isRequired: true` ولا تحقق لا في الواجهة ولا في الخادم.

**القرار:** تحقق على الخادم. الحقل الإلزامي الفارغ يمنع التوليد ويعيد رسالة واضحة.

### ق11 — دفاع بنيوي ضد الحقن

**المشكلة [مقيس]:** سَهَل نجا من الحقن لأن **النموذج** تصرّف بذكاء، لا لأن المعمارية تمنعه. دفاع يعتمد على حكم النموذج في كل مرة دفاع هش.

**القرار:**
- إجابات المستخدم تُمرَّر داخل كتلة بيانات محدَّدة بوضوح (`<user_data>…</user_data>`) مع تعليمة صريحة بأن ما بداخلها بيانات لا أوامر.
- نص المستخدم **لا يُنسخ أبداً** إلى حقول التعليمات التي تُحقن لاحقاً في توليد المحتوى. حقول التعليمات تُبنى من الحقول المهيكلة في ق8 فقط.
- فحص أنماط الحقن قبل الحفظ، ووسم الهوية للمراجعة عند الاشتباه.

### ق12 — وسّع مجموعة الأسئلة

خمسة أسئلة لا تكفي. الغائب الذي يرفع جودة كل المحتوى اللاحق: الجمهور المستهدف، المنافسون، النبرة، الممنوعات، نطاق الأسعار، المدن المخدومة.

### ق13 — نوع النشاط قابل للتعديل

**المشكلة [مقيس]:** تغيير النوع في سَهَل يتطلب حذف الهوية نهائياً.

**القرار:** نوع النشاط حقل عادي قابل للتعديل كأي حقل آخر. وفي مسار الخدمات: قائمة **مفتوحة** (dropdown + «أخرى» نص حر) لا قائمة مغلقة.

## 3. معايير القبول — ثوابت يجب أن يتحقق منها الكود

هذه قابلة للتحويل إلى اختبارات آلية مباشرة:

| # | الثابت | طريقة الاختبار |
|---|--------|----------------|
| T1 | مدخلات متطابقة ⇒ مخرج المرحلة 1 متطابق | شغّل الاستخلاص 3 مرات، قارن الـ JSON |
| T2 | حقل إلزامي فارغ ⇒ لا توليد، رسالة خطأ | طلب بحقل فارغ ⇒ 422 |
| T3 | حقل غير مذكور ⇒ لا جملة تسويقية عنه | مدخل الاسم فقط ⇒ المخرج يذكر الاسم ولا يخترع شخصية |
| T4 | تغيير الرابط ⇒ تغيّر الحقائق المستخرجة | رابطان مختلفان ⇒ `source: website` مختلف |
| T5 | حقن تعليمات ⇒ لا يظهر في أي حقل تعليمات | أدخل نص حقن ⇒ تحقق أن حقول التعليمات نظيفة |
| T6 | كل إصدار قابل للاستعادة | أنشئ، عدّل، استعد، قارن |
| T7 | مخرج التوليد يطابق المخطط دائماً | تحقق بـ JSON Schema في كل مسار |
| T8 | التناقض يُرصد ويظهر للعميل | أدخل تصنيفاً يناقض المزايا ⇒ `conflicts` غير فارغ |

## 4. جدول الفجوة مقابل الفرصة

| فجوة في سَهَل Ai [مقيس] | فرصة Marketer AI | الأثر على العميل | الجهد |
|------------------------|------------------|------------------|------|
| الرابط يُنسخ ولا يُقرأ | قراءة الموقع واستخراج المنتجات والنبرة | يراه في أول دقيقة | متوسط |
| L2/L3 تخترع عند نقص المدخل | مرحلتان + قاعدة null | محتوى بلا ادعاءات كاذبة | متوسط |
| لا تطبيع للمصطلحات | قاموس تطبيع | جودة أعلى بلا جهد من العميل | منخفض |
| لا إصدارات ولا تراجع | `identity_versions` + مقارنة | ثقة في التجربة | منخفض |
| النوع مقفل بعد الإعداد | حقل عادي قابل للتعديل | يزيل إحباطاً حقيقياً | منخفض |
| أقوى حقل اختياري ومخفي | حقول قواعد محتوى مهيكلة | تحكم فعلي بالنبرة والتركيز | متوسط |
| الهوية غير قابلة للاستنساخ | حرارة منخفضة + تخزين | استقرار | منخفض |
| 5 أسئلة فقط | جمهور + منافسون + نبرة + ممنوعات | كل المحتوى اللاحق أدق | منخفض |
| تصنيف الخدمات قائمة مغلقة | قائمة مفتوحة + نص حر | تخصص دقيق يصل للسياق | منخفض |
| حقل مخفي لا يراه العميل | اعرض التعارضات والافتراضات | شفافية وثقة | منخفض |
| البرومبت يُبنى من بيانات العميل | البرومبت ملك الخادم | أمان | منخفض |

**أفضل نسبة أثر/جهد للبدء:** ق4 (قراءة الرابط) + ق1 (المرحلتان) + ق6 (الإصدارات). الثلاثة معاً يصنعون منتجاً يُحسّ الفرق فيه فوراً.
